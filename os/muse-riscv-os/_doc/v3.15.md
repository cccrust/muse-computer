# muse-riscv-os v3.15（主線：install 全鏈 TLS —— `ctr installs`）

## 0. 動機

v3.14 證明了 guest TLS 取包鏈路（`wgets` 抓 manifest/tar），但
`ctr install` 全鏈仍走明文 8091——取包的人有 TLS、用包的人沒有。
本版把最後一哩接上：`installs` 與 `install` 同語義、同 staging、
同 db，差別只在 fetch 層。

## 1. 語義

- `ctr installs <host> <tlsport> <pkg>[=ver]`（`install` 的逐字鏡像；
  `=ver`/`>=ver` 解析、`valid_name`/`ver_valid` 檢查沿用同一份）：
  index → manifest → layers → 依賴 DFS → staging `.new` → db，
  每一路 fetch 改 fork `/bin/wgets`（`run_wgets`，與 `run_wget`
  同 argv 形狀：`<host> <port> <path> <outfile> [token]`；
  token 照舊取 `/pkg/token` 首行）。
- 線程方式：`run_wget(…, secure: bool)` 分派 + `secure` 穿過
  `install_one`/`fetch_index`/`fetch_layer`（遞迴依賴一併走 TLS；
  `upgrade_one` 傳 `false`，行為逐位元不動）。
- TOFU pin + 牆鐘：`wgets` 內部處理（明文 `:8091/time` +
  `/rootcert` side channel，`PLAIN_PORT` 寫死——與 v3.14 直接
  調用同一假設：registry 明文與 TLS 同機）。
- 不動：`ctr pull`（image 路徑，自有用 `run_wget` 的兩處）、
  `ctr upgrade`（`upgrades` 另立版）、registry（:8443 早已 serve
  全路由）、kernel TCP（零改）、`wgets` 本體（零改）。

## 2. suite（確定性設計）

```
ctr installs 10.0.2.2 8443 farewell → pkg-installed farewell 1.0
farewell farewell-marker              → farewell-marker
ctr remove farewell / remove hello    → pkg-removed farewell / hello
```

- 位置：sh autorun v3.14 段之後（db 是乾淨的：v3.13 移除了 hello；
  token 殘留無害）。farewell 會把 hello=1.0 當 auto-dep 拉進來，
  流程結束補 `remove hello` 清 db（v3.1 同款編排）。
- test.sh +1 項（run1）：`wgets PASS farewell.tar`。唯一性論證：
  該字串只能由 fetch 路徑以 `farewell.tar` 結尾的 `wgets` 子進程印出，
  全 suite 只有 `installs farewell` 走這條路（v3.14 直接調用只抓
  manifest + hello.tar）；`pkg-installed/run/remove` markers 沿用舊字串。
- 手動：`installs` 指到明文埠（TLS handshake 對 HTTP 必 loud 失敗）、
  私包 `installs`（token 路徑與明文同）。

## 3. 非目標（→ v3.16+）

- `ctr upgrades`（upgrade 全鏈 TLS）、TLS session resumption、ALPN、
  client cert。
- 真 RNG（virtio-rng）、真 RTC/NTP、Ed25519/SHA-512、cipher agility、
  證書吊銷/OCSP、SNI 多域（v3.14 §3 原樣順延）。

## 4. 驗收

- `./test.sh` 全綠（122+1=**123 項**），零 `PANIC`/`FAIL`，連跑 2 輪。
- fast gate 先行（`guest-tls` 未動，RFC 向量仍綠）。
- 舊測項零退化（重點：`install`/`upgrade`/`pull` 路徑逐位元同舊；
  `secure=false` 分支與舊 `run_wget` 同碼）。

## 5. 落地備註（本版真正的 bug：32-slot socket 耗盡）

- 現象：`installs` 在同一 fetch（不是同一包、不同輪是第 3/4 個
  fetch 交替）`wget FAIL (connect)`，fast boot 必現、slow boot 過。
  探針（`socket()` 失敗時再 `open()`，事後已還原）指向全局
  NSOCK 耗盡，不是進程表滿。
- 根因（兩層疊加，皆 pre-existing，v3.15 的 fetch burst 引爆）：
  1. exit 不回收 socket：子進程 `fail()` 直接 exit，ESTABLISHED-IDLE
     的 slot 永不超時、永不釋放（每 boot 漏數個）。
  2. close 後 30s lingering：fast boot（34s 跑完全 autorun）結束時，
     全 boot 幾乎所有 socket 都還在 lingering 窗內；installs 的
     5 連發（×3 sockets）正好把第 32 槽用完。
  慢 boot 能過只是因為早期的 lingering 剛好過期——不是沒病。
- 修法（kernel，`installs` 本體未動）：
  1. `task waitpid` reap 時關掉死進程的 kind-7 fds（`sock_close`；
     已有守衛：重複關是 no-op；fork 共享的 live-slot 別名是已記載
     的 hazard，當前 tree 無此模式）。
  2. `sock_open_kind` 無空槽時回收最老的 closing TCP slot
    （FinW1/FinW2/Closing/LastAck + fd-detached；RST + 重用，
     live態永不偷）。平時行為不變，滿表才觸發。
- 診斷過程的教訓：stub 全死時 autorun 反而飛快（RST 快速失敗），
  stub 半殘/高負載時 retry-burn 看起來像 hang；判 hang 前先查 stub
  存活 + host load。
- 【未解，v3.16 候選】`ctr run -v` 段偶發全凍結：QEMU monitor 證實
  4 hart 同卡 `sched_lock::lock_counted`（PC `0x80217e72`，至少一 hart
  scause=5 timer 中斷內自旋——中斷重入自死鎖或 AB-BA），log 凍結 90s+、
  無 PANIC。新 image + host load ~4.6 可復現，低負載 12+ boots 全過；
  v3.14 二進位也出現過（r2 qemu4/qemu7 同徵兆），故為 pre-existing
  的 scheduler 中斷紀律問題，非 v3.15 引入（v3.15 只改了時序分佈）。
  真修要在 lock primitive 層面處理 SIE（影響所有臨界區，需另立版
  審計）；本版 suite 綠燈依賴低負載窗口。
