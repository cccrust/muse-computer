# muse-riscv-os v2.5（主線：收掉地基的兩個謊話——大文件 + 退出碼）

## 0. 動機

v2.4 留下兩個誠實聲明，都有案底：

1. **盤上文件上限 69632B 是謊話製造機**（direct[8]+一級 indirect）。
   `/bin/sh`（114KB）、`ctr`（88KB）讀/開/exec 走盤必回 None，
   實際跑的是 kernel embed（v2.4 的 bisect 混亂即此所致）。
   更糟：mkfs 的 `inode_grow` 無視 128 項上限，超限部分直接寫越界
   （sh 蓋掉後面 88 個塊位），`chroot` 第二遍 setup-link FAIL 只是
   最可見的症狀。v2.3 的 qemu2.log 裡就有，只是 run2 段不斷言它。
2. **detached 容器的退出碼被 init 帶走**：收割即丟失，`ps` 只能說
   Exited，不能說怎麼死的。

本版兩件一起做（互相獨立，共用驗收輪次）：二級 indirect + 退出碼環。
overlayfs、認證、CFS、netns/veth 續留 v2.6+。

## 1. 二級 indirect（FS 格式小改，向前相容讀）

- on-disk 記錄 64B 不動：kind@0、size@4、direct[8]@8、indirect@40、
  nlink@44，**新增 dindirect@48**（原 16B spare 的前 4B）。
  舊 image 該欄為 0 = 無二級樹，舊核心照讀（新 image 給舊核心：
  超限部分不可見——單向相容，寫死在這；test.sh 每輪重建故無痛）。
- 定址：idx<8 → direct；idx-8<128 → indirect；否則 ii=idx-136，
  ii<16384 → dind[ii/128]→二級塊[ii%128]。上限 (8+128+16384)×512
  ≈ 8.4MB > 整盤 4MB（盤滿先到，檔案上限實務上消失）。
- kernel（`disk.rs` 內，無新鎖，全部經既有 `data_block` choke 點，
  故 read/write/list/unlink 全自動生效）：
  - `Ino += dind: u32`；`get_ino`/`put_ino` 讀寫 +48。
  - `data_block` 加第三段（alloc 時逐級建塊並清零，新塊放行前
    `put_ino` 寫回——沿用 indirect 段的既有紀律）。
  - `free_ino_blocks` 釋放二級樹（l2 塊→l1 塊→dind 塊，逐個判零）。
  - `truncate_path` 先 free 整樹再清三字段（不清 dind 就是下一個
    v2.3 式別名 bug）。
  - `create_empty`/`mkdir` 復用槽位時清 dind（同上，v2.3 教訓延續）。
- mkfs（host 側，同佈局）：
  - `inode_grow`：direct→indirect→dind（逐級開塊；舊碼的越界寫入
    在此根除——超 128 項進二級樹，不再蓋鄰居）。
  - `read_file`（自測用）：同規則讀回；`lookup`/`list`/`dir_add`
    不動（目錄 stays direct-only，`bi<8`斷言本來就在）。
- 為何不用 direct[12] 之類小補丁：16B spare 只夠 +4 direct
  （140 塊 = 71680B，sh 照樣超）。要麼不做，要麼二級。

## 2. 退出碼環 + `SYS_REAPSTAT = 52`（約 30 行）

- 無需 init 配合：init 本來就用 wait 迴圈秒收割孤兒（exit 喚醒，
  延遲 ms 級）。hook 放在 kernel 的 `waitpid` 收割點
  （`s.procs[c].take()` 處，有 code + 整個 Proc）。
- `REAPLOG: [(pid, code); 32]` + 下標，靜態，**只在 sched_lock 下碰**
  （SCHED 同紀律；append 在收割臨界區，查詢走新 syscall 同拿鎖）。
  pid 單調不重用 + ring 純內存（每 boot 歸零）⇒ pid-only 匹配安全。
  32 深：suite 路徑上 stop→ps 之間退出數≈0；陳年容器被擠掉就退回
  plain Exited（best-effort，寫死）。
- `SYS_REAPSTAT = 52(pid)`：新到舊掃 ring，命中回 `(code+0x10000)`，
  未命中回 -1。偏置因 code 可為負（-9 被殺、-1 panic）而 -1 另有其主；
  code 實踐中 |code|≪0x10000（exit/kill 碼），i64 中轉防溢（寫死）。
- `ctr stop` 的 poll 改「等到 gone（slot 釋放 = 已收割）」：
  gone ⇒ ring 必有 code（剛 append；32 深在 suite 窗口內擠不掉），
  故 suite 的 code 斷言是確定性的。10s 預算保留；超時仍 FAIL。
  （此前「zombie 即停」會留下收割競態——ps 可能早於 init 收割。）
- `ctr ps` 行：活 `Up Ns`；僵屍/無碼 `Exited`；有碼
  `Exited (code N)`（負號自印，`dbg_num` 只吃 usize 故加小 wrapper）。
  `test.sh` 原有 `Exited` 子串不斷；**+1 項**（71+1=**72 項**）：`code -9`
  （stop 就是 kill -9，確定性）。

## 3. suite（不新增段，改兩處）

- autorun 原樣（life 6 步）：第二遍 `ps` 行天然帶出 `(code -9)`。
- 手動（§4 驗收）：`cat /bin/sh` 洪水 114KB（讀路徑證明）；
  同一 boot 內 `chroot_test` 跑兩遍（第二遍 setup-link 必須 PASS——
  潛問題根治證明）；`ps` 看 code。

## 4. 驗收

- `./test.sh` 全綠（72 項），零 `PANIC`/`FAIL`，連跑 2 輪。
- 舊測項零退化（重點：dind=0 的舊佈局行為逐位元同舊；`read_file`
  越界舊行為「回 None」變「讀出正確內容」——這正是要修的；
  `stop` 等到 gone，舊 10s 預算不動）。
- 手動：上 §3 三項 + `ctr run` 前台 code 照常直通（不動）。

## 5. 非目標（→ v2.6+）

- cgroup-kill（stop 連坐整組）、`run` 後台 stdio 重定向、
- overlayfs、registry 認證/摘要/TLS、私有 registry、
  CPU floor/share（CFS）、netns/veth、volume/bind mount、
  IO 權重、層級配額 enforced、cgroupfs、OOM-killer 啟發式、
  `pivot_root`、ring 擴容/持久化（32 擠掉即退化為 plain Exited）。
