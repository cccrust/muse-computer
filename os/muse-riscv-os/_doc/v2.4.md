# muse-riscv-os v2.4（主線：ctr 生命週期——run -d、ps、stop、rm）

## 0. 動機

v2.3 的 `ctr run` 是前台一次性：跑完即回收，看不到、停不掉、刪不掉。
本版把管理面補齊：後台跑（`-d`）、列表（`ps`）、停（`stop`）、刪（`rm`），
外加欠賬回收（空 ns 槽位重用、unlink 目錄塊洩漏）。
overlayfs、registry 認證、CPU floor/share、netns/veth 是 v2.5+ 議題。

## 1. 狀態文件（user 側，不進內核表）

- `ctr run -d` 的父進程（shell 的孩子）在 fork 後寫 `/ctr/<name>/.pid`：
  內容一行 `"<pid> <start> <name>\n"`（十進制，global pid + 見 §2）。
  寫完印 `detached <pid>`、exit 0；容器 pid1 隨 ctr 退出 reparent 到 init，
  由 init 的 wait 迴圈收割（v1.2 機制，照用）。
- 寫 state 失敗（盤滿之類，幾乎不可能）→ 先 `kill` 掉剛 fork 的孩子再 exit 1，
  不留孤兒（ hygiene，寫死在這）。
- state 跨 reboot 即 stale（pid 從頭編號）：`ps` 靠 (pid,start) 雙比對認人，
  認不出即 `Exited`（見 §2 誠實聲明）；`rm` 清掉即了事。
- 前台 `run` 不寫 state（語意不變）；`pull`/組裝的镜像無 `.pid`，
  `ps` 自動跳過（`open` 失敗即不是容器）。

## 2. `SYS_PIDINFO = 51`（唯一新 syscall，約 15 行）

- 動機：`ps_snapshot` 只列**同 ns**（v2.1 視圖），root ns 的 `ctr ps`
  看不見新 ns 裡的容器 pid1；`kill(pid,0)` 語意不存在；`waitpid` 只收自己孩子
  （detached 容器已過繼給 init）。liveness 只能問內核。
- 語意：`pidinfo(global_pid)` → `+(start+2)`（活：Running/Runnable/Blocked）、
  `-(start+2)`（僵屍：init 馬上會收）、`-1`（槽空/越界：已收割或從未存在）。
  `start` = fork/spawn 時的 `timer::ticks()`（`Proc.start_ms: u64` 新欄位，
  兩處 `Proc{}` 字面量——fork 與 finish_spawn——同設）。
- 為何帶 start：pid 單調不重用（`next_pid`，同 boot 內 stale pid 永遠指不到
  別人）；跨 boot 才需雙比對。`+2` 偏置讓 `-1` 永遠只表示 gone（start=0 的
  僵屍也不會撞）。
-   `user-lib::pidinfo(pid)`；kill 仍走舊路（global pid fallback 在 ns0 無 lpid
  碰撞：global pid 全機唯一，佔了 G 的只有容器 pid1 自己，退回分支必中）。

## 3. `ctr ps / stop / rm`（約 250 行，全 user 側）

- 子命令名保留：`ps/stop/rm/run/pull` 不再能當裸 `ctr <name>` 的容器名
  （此前 `ctr ps` 會組裝名叫 ps 的容器；docker 同理，`docker ps` 不是镜像名）。

- `ps`：`getdents(/ctr)` → 逐項試 `open(/ctr/<e>/.pid)` → 解析 → `pidinfo` →
  印表 `NAME PID STATUS`（STATUS = `Up <s>s` / `Exited`，`Up` 秒數來自
  `time()` 差值，只供人看、不進斷言）。行前綴 `CTRPS `（test.sh 行級 grep，
  見 §5；`Up`/`Exited` 全 log 無碰撞——v2.3 log 實測 0 命中）。
- `stop <name>`：讀 state → `kill(pid)` → poll `pidinfo`（1s 間隔，10 次）→
  印 `stopped <name>` exit 0。已 gone → 印 `stopped <name> (already exited)`
  exit 0（冪等，重跑不炸）。超時 → `ctr: stop timeout` exit 1。
- `rm <name>`：state 存在且 pid 活 → `ctr: running (stop first)` exit 1
  （先停後刪，docker 同款）；否則遞迴刪 `/ctr/<name>`（getdents 逐項：
  先刪孩子再 unlink 自己，`.pid` 只是普通文件順手刪）→ 印 `removed <name>`。
- 誠實限制（寫死，不修）：`stop` 只殺 pid1，孫進程過繼給 init 繼續活
  （真 cgroup-kill 要 pid→cgroup 反查，是 v2.5 議題）；exit code 不保留
  （init 收割時帶走，要 code 用前台 run）；`Up` 秒數是人看的。

## 4. 附帶修（順手不繞路）

- ns 槽位重用（v2.1 欠賬）：fork 建新 ns 時先掃描零引用槽（live proc
  含僵屍都算引用，0 號保留）→ 重用（重置 parent/next），否則 push。
  Sound 的理由：分配與佔用是原子的——佔用者（正出生的孩子）在同一把
  sched_lock 下插入，無 enter 可插縫。長 uptime 下反覆 `run -d/stop/rm`
  不再無界增長。
- cgroup 槽位**不**重用（試過又 revert，有案底）：create 與 enter 是兩次
  syscall，「當下無人引用」看不見未來意圖——標準的 create→fork→child-enter
  模式會把兩個組併進同一槽（實測：cgtest 的 cap/free 兩組合併，
  `cg FAIL (cpu-order)`，A/B 對照 v2.3 內核確認）。保持 v2.2 push-only；
  增長實踐中有界（容器繼承不新建，create 只出現在自測/手動）。
- `unlink` 目錄分支補 `free_ino_blocks`（原只清 inode，數據塊洩漏；
  `rm` 遞迴刪大镜像時每目錄漏數塊，順手堵上；文件分支語意不動）。
- `ctr` 組裝/ps/rm 的 getdents 迴圈修 count-vs-bytes（v2.0 潛 bug：
  `r` 是項數不是字節數，舊碼拿字節偏移去比，只連前幾個——`echo` 第 5
  剛好擠進，`sleeper` 第 22 個永遠連不上；`ctr run` 報 exec failed。
  ps 同 pattern 順手修；rm 因外層「刪到空為止」本來就自洽，改成精確
  只是少跑一輪）。
- 新 `user/sleeper`（約 30 行）：`sleeper <secs>` → `sleep` → `exit(0)`，
  零輸出（suite 的安靜長跑目標；`/bin/cat` 擋 stdin 會啃 console，
  `stress` 太吵——都不合適）。mkfs 名單 + workspace + run/test build 單同步加。
- mkfs inode 備額 16→64（`Image::new` 一行）：穩態運行文件約 14 個
  （/tmp、/ctr、testimg×4、ctrtest×2、dl.txt、WD×3、CRASHDAT、TESTDATA）
  加 suite 瞬態 3 個（life、bin、.pid）= 17，舊備額直接見頂——
  用過的 image 上 `.pid` 建不出來（`detached state failed`，初查誤判為
  腐蝕，實為 inode 耗盡；讀寫路徑無辜）。讀端全走 superblock，無硬編碼。

## 5. suite（autorun 尾段，確定性；poll 只等狀態翻轉）

```
ctr life                          # 組裝（含 /bin/sleeper，零拷貝 link）
ctr run -d life /bin/sleeper 30   # → `detached <pid>`
ctr ps                            # → `CTRPS life <pid> Up`
ctr stop life                     # → `stopped life`
ctr ps                            # → `CTRPS life <pid> Exited`
ctr rm life                       # → `removed life`
```

- 全同步、無時序：每步 `run_args` 等前一步 exit 才走；`ps` 在 fork 後
  立即可見活槽（state_alive 只需槽活著，不需 exec 完成）；`sleeper 30`
  的 30s 是上限，stop 馬上殺（stop 內 poll 10s < 30s，自洽）。
  test.sh 只 grep marker 行（`Up`/`Exited` 全 log 無碰撞，v2.3 log 實測 0 命中）。

- test.sh +6 項（65+6=**71 項**）：`detached `、`CTRPS life`、`Up`、
  `stopped life`、`Exited`、`removed life`。失敗路徑只印 `ctr: ...` 不印 marker，
  缺 marker 即 FAIL（img 式 house style）。

## 6. 驗收

- `./test.sh` 全綠（71 項），零 `PANIC`/`FAIL`，連跑 2 輪。
- 手動：`run -d` 後關 shell 重進，`ps` 仍在（state 在盤上）；`rm` 跑著的被拒；
  反覆 20 次 run -d/stop/rm 後 `[CG] groups=` 不漲、ns 不漲（`halt` 行看組數；
  ns 無行，加 `ps` 行為證即可）。
- 舊測項零退化（重點：`Proc` 加欄位不動佈局語意；unlink 文件路徑逐位元同舊；
  `ps_snapshot` 不動）。

## 7. 非目標（→ v2.5+）

- 已知潛問題（v2.3 起，test.sh 不斷言，順手記在這）：盤上文件上限
  (8+128)×512 = 69632B（direct[8]+一級 indirect）；`/bin/sh`（~114KB）
  超限，讀/開/exec 走盤必回 None，實際跑的是 kernel embed（編譯期灌入，
  test.sh 先編 user 再編 kernel 故新鮮，但手改 sh 不重編 kernel 會跑舊的——
  v2.4 debug 期的 bisect 混亂即此所致）。症狀：`chroot` 自測第二遍
  （link 已存在→走 open 驗證→讀不出 sh）報 setup-link FAIL（v2.3 的
  qemu2.log 裡就有，只是 run2 段不斷言它）。根治要改 FS 格式
  （二級 indirect），動 mkfs+kernel+全部镜像，v2.5 議題。

- cgroup-kill（stop 連坐整組）、exit code 保留（`ps -a` 帶 code）、
  `run` 後台 stdio 重定向（目前繼承 console，會交錯——用安靜程序是約定）、
- overlayfs、registry 認證/摘要/TLS、私有 registry、
  CPU floor/share（CFS）、netns/veth、volume/bind mount、
  IO 權重、層級配額 enforced、cgroupfs、OOM-killer 啟發式、`pivot_root`。
