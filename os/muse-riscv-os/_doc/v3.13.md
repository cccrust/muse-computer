# muse-riscv-os v3.13（掉電原子性：staging 重放）

## 0. 動機

#2 問題：`rollback` 只包乾淨失敗路徑。`kill -9` 打在解包一半、
`upgrade` 覆寫 store 到一半時——store 是撕裂的，db 卻可能已指向
新版，且無修復工具。本版用 staging 協議把「引用到撕裂狀態」
變成不可能（FS 沒有 rename syscall，真原子做不到；做到
可檢測 + 可自愈 + 永不引用）。

## 1. 語義

- Staging 目錄：`/pkg/<name>.new/`（`.new` 後綴；同名包禁叫
  `.new` 結尾——install/upgrade dispatch 拒收，`ctr: bad name`）。
  創建語義：mkdir 失败 → 查父目錄列表——已存在即有人在装，
  `ctr: install in progress` 大声拒绝（mkdir 本身原子，并发安全）；
  殘留舊 `.new`（上次被殺）→ 先 `rm_all` 清掉再建（自愈入口）。
- Install 提交顺序（db 永远最后）：
  下载 → verify → 解包进 `.new` → 写 files/manifest → 逐文件
  link 进正式 store（同 FS，link+unlink 單文件；崩在中間至多两边
  并存同 inode，無丟失）→ shadow 检查 → 建 /bin 链接 →
  db add →清 `.new` 殘餘。任一步失败 loud，中途崩溃留下的
  `.new` 下次同包 install 自清。
- Upgrade 同协议：新版解进 `.new` → 新依赖先装 → GC 比对
  （旧 files-list vs 新 tar 扫描）→ 新文件搬入 → 刪 stale →
  relink 全部 → files/manifest/db 更新（db 最后）→ 清 `.new`。
- `ctr verify [<pkg>]`（唯讀检查器，無修复写）：
  对 db 中每包（或指定包）查：store/`files`/`manifest` 存在；
  files 清單每項在 store 存在；store/bin 下每项在 /bin 可 open；
  db 行格式合法。不通過即 `verify-fail <name> <reason>` exit 1；
  全過印 `verify-ok <name> <ver>` 逐行（單寫，suite grep 整行）。
  `.new` 殘留只報告（`orphan <name>` 行），不自動刪
  （刪的動作是下次同包 install 的自清；verify 保持唯讀）。
- 非目標：真原子 rename（要 `SYS_RENAME`，另立版）、verify 自動
  修復、跨包事務、db 文件自身的掉電撕裂（單行追加，容忍）。

## 2. suite（確定性設計：verify 綠 + 舊 marker 全過即證明）

```
ctr install 10.0.2.2 8091 hello=1.0   → pkg-installed hello 1.0
ctr verify hello                       → verify-ok hello 1.0
ctr remove hello                       → pkg-removed hello
```

- test.sh +1 項（run1）：`verify-ok hello 1.0`。
  staging 協議本身由**所有既有 install/upgrade marker**覆蓋
  （全走新路徑：壞了就全紅——這就是最強的確定性證明）。
- kill -9 中途：「下次同包 install 自清」走手動（時序 flake，
  不进 suite；§11 同款理由）。
- 手動：并发同包 install（第二個 `install in progress`）、
  `verify` 壞包（刪 store 一文件後報 fail）、`.new` 結尾包名拒絕。

## 3. 非目標（→ v3.14+）

`SYS_RENAME`、verify 自动修复、db 自身 journal、跨包原子。
